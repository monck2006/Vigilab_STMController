# C1 运动控制方案与代码逐步讲解

这份说明回答四个问题：STM32 在机器人里负责什么、为什么要重写固件、代码每一步在做什么、拿到板子后按什么顺序使用。它对应当前仓库源码；不是对真机性能或安全性的认证。

## 一句话先理解

树莓派告诉 STM32“左右轮希望多快”，STM32 通过编码器测“左右轮实际多快”，再调整 PWM，让两边轮速跟上目标。这个反馈过程叫**闭环速度控制**。

```text
树莓派目标轮速
      ↓ USART3
STM32 收命令 → 目标速度斜坡 → PI 控制 → TIM3 PWM → BTS7960 → 电机/车轮
                                  ↑                         ↓
                                  └──── TIM2/TIM8 编码器 ───┘
      ↑ USART3 状态、轮速、里程
```

树莓派负责 ROS2 导航、建图、避障和决策；STM32 不知道机器人要去哪里，只负责按要求控制左右轮并报告轮速/里程。

## 为什么要写这份代码

原工程里有些注释描述的是“计划要做的功能”，实际代码却没有做到；另有几处引脚和参数与开发板资料不一致。继续在旧代码上零散修补，很难判断一条速度命令到底会发生什么。因此这次把代码按信号流重新组织，并把尚未确认的硬件条件放在明处。

| 原工程的问题 | 会造成什么 | 这版代码怎么处理 |
| --- | --- | --- |
| 编码器代码按 11 PPR，资料截图标的是 16 PPR，且每轮计数没有实测 | 速度反馈和里程换算会整体偏差，PI 跟错的速度 | 改用单一参数 `ENCODER_COUNTS_PER_WHEEL_REV`；当前先填 3584，但明确标成待校准假设 |
| 编码器 100 Hz 更新，速度环 200 Hz；安全任务 1 kHz 反复看同一个旧增量 | 测速和堵转判断使用的数据节奏不一致 | 同一个控制任务读取编码器并运行速度环，目标周期 20 ms；安全超时仍按 1 ms 节拍检查 |
| 旧 PI 积分每次简单加 `Ki × error`，没有乘实际采样时间 | 改变控制频率就改变了控制器强度，参数含义不清楚 | 使用 `I += Ki × error × dt`，并限制积分和 PWM 输出 |
| 配置里有加速度参数但没有用；软停直接切 IDLE | 目标速度可能阶跃，停车行为与文档不一致 | 加入目标速度斜坡；`CMD_STOP` 进入 STOPPING，速度降下来后再进 IDLE |
| 用 PWM 占空比估电流，但最大估计小于保护阈值；状态电压写死 | 看起来有保护，实际条件不可能触发，电压也不是真实测量 | 删除虚假的电流估算和固定电压；电压用 `0xFFFF` 表示未知 |
| 把 PA0 当作电机电源开关；开发板原理图把 PA0 引作 UART4_TX | 固件拉 PA0 不一定能切断驱动电源，还可能占用串口脚 | 默认关闭 PA0 开关控制；软件急停与硬件断电急停分开说明 |
| PA5/PF11 EN 和触摸屏复用；多个发送点共用 DMA 缓冲 | 可能占用板载功能；多个发送同时发生时数据可能冲突 | 默认不接管 EN；UART 发送统一进入队列，由一个 Telemetry 任务发送 |

这次重写的目标是先把“收到的目标速度 → 测得的实际速度 → PI 输出 → 电机 PWM”连成一条易读、可校准的路径。参数调好、引脚确认和硬件保护接入仍需实物联调。

## 代码从上电到转动的顺序

### 1. `main.c` 建好外设

`main()` 初始化 MCU 时钟、USART3、TIM3、TIM2、TIM8、TIM7 和独立看门狗，再调用 `App_Init()` 创建任务和队列，最后启动 FreeRTOS。

- USART3（PB10/PB11）收上位机命令。
- TIM3 四个通道（PB4/PB5/PB0/PB1）输出两台电机的 PWM。
- TIM2、TIM8 分别读取左右编码器 A/B 相。
- TIM7 产生 1 ms 节拍，唤醒控制任务。

调度器启动后，Control 任务才启动串口接收和 TIM7，避免系统调度器尚未运行时就在中断里调用 FreeRTOS 队列/通知接口。

### 2. 串口中断只收字节，不控制电机

USART3 每收到一个字节，`HAL_UART_RxCpltCallback()` 就调用 `App_OnRxByte()`。协议解析器寻找 `AA 55` 帧头、读取长度并核对 CRC16；只有完整且正确的帧才进入接收队列。

例子：

```text
AA 55 06 01 01 C8 00 C8 00 28 B1
```

- `AA 55`：帧头。
- `06`：长度为序号 1 字节、命令 1 字节、数据 4 字节。
- `01`：序号。
- `01`：设置轮速命令。
- `C8 00`：左轮 200 mm/s（小端有符号整数）。
- `C8 00`：右轮 200 mm/s。
- `28 B1`：CRC16 校验。

### 3. `Task_Control` 处理命令和安全状态

它每次被 TIM7 唤醒都会取出等待处理的命令，并检查通信是否超时。主要命令如下：

| 命令 | 代码行为 |
| --- | --- |
| `0x01 SET_SPEED` | 将左右轮目标限制在 ±1000 mm/s，进入 RUN，打开软件输出许可 |
| `0x02 STOP` | 将目标置零并进入 STOPPING，经过斜坡减速 |
| `0x03 ESTOP` | PWM 立即清零、锁定软件输出 |
| `0x04 CLEAR_ESTOP` | 两侧测得速度都不超过 20 mm/s 时清除锁定 |
| `0x05 RESET_ODO` | 左右累计里程清零 |
| `0x06 SET_PID` | 更新 PI 参数，不保存到 Flash，重启后恢复默认值 |
| `0x07 HEARTBEAT` | 续期通信超时计时 |
| `0x11 QUERY` | 立即排入一帧状态 |

在 RUN/STOPPING 时，500 ms 没有合法串口帧会开始软停；1 s 仍未恢复则进入锁定故障。上电后一直处于 IDLE 时，不会因为树莓派启动慢而误报通信故障。

### 4. `encoder.c` 把计数变成速度和里程

定时器在硬件里自动累计 AB 相变化；每次控制更新时，程序读取计数器的新旧差值：

```text
每计数距离 = π × 轮径 / 每轮计数
速度(mm/s) = 计数增量 × 每计数距离 / 采样时间(秒)
累计里程(mm) = 累计计数 × 每计数距离
```

当前轮径为 180 mm，暂定每轮计数 3584，因此一圈按 `π × 180 ≈ 565.5 mm`，每个计数约 `0.158 mm`。例如 20 ms 内增加 10 个计数，反馈速度约为 `10 × 0.158 / 0.020 = 79 mm/s`。

**3584 不是已经确认的事实。** 它是假设 16 PPR 指电机轴每转的脉冲数，并按 A/B 四倍频和 56:1 减速比计算。当前状态协议没有直接上报定时器原始计数；可以先将轮子准确转一整圈，比较里程读数与理论周长 565.5 mm，再按比例更新。更长直线行驶标定可用 `tools/encoder_calib.py`。

### 5. 斜坡限制目标变化

配置最大加速度为 300 mm/s²，控制周期约 20 ms。因此每次目标最多变化：

```text
300 mm/s² × 0.020 s = 6 mm/s
```

目标从 0 跳到 200 mm/s 时，控制器会逐步看到 6、12、18……直到 200 mm/s，而不是一次跳到 200。此限制作用在“目标速度”，不保证车轮真实加速度恰好等于该值。

### 6. PI 把速度误差变成 PWM

```text
e = 斜坡后的目标速度 - 编码器实测速度
I = I + Ki × e × dt
PWM = 限幅(Kp × e + I)
```

例如目标 200、实测 150 mm/s，误差是 50 mm/s；`Kp=0.30` 时比例项是 15‰。若积分初始为 0，采样为 20 ms、`Ki=2.0/s`，这一周期积分增加 `2 × 50 × 0.020 = 2‰`，未限幅前输出约 17‰。‰ 表示 PWM 千分比，1000‰ 是 100%。

- P 项让输出立即响应当前误差。
- I 项逐步补偿长期误差。
- 积分限幅和抗饱和避免输出已到上限时积分继续堆积。
- 默认 Kp/Ki 是起始值，尚未实车整定；轮径、每轮计数、方向和接线未确认时不要用调 PI 来掩盖问题。
- `PWM_DEADZONE_PERMILLE` 默认 0，因为电机死区还没有实测。低占空比时真实电机可能克服不了静摩擦，需要后续测量、记录后再填。

### 7. `motor.c` 把 PWM 正负号变成 H 桥输入

- 正占空比：RPWM 输出 PWM，LPWM 为 0。
- 负占空比：RPWM 为 0，LPWM 输出 PWM。
- 0 占空比：RPWM、LPWM 都为 0，自由滑行。
- `MOTOR_LEFT_SIGN` / `MOTOR_RIGHT_SIGN` 用来修正电机物理接线方向。

每个轮子的电机方向和编码器方向是两件事：电机 sign 修“命令正方向”，encoder sign 修“反馈正方向”。机器人向前时，两侧都应呈现正目标、正反馈。

### 8. `Task_Telemetry` 统一发送

控制任务把 ACK 或状态包放入发送队列；Telemetry 是唯一调用 UART 发送接口的任务。状态每 50 ms 上报一次。电压字段当前写 `0xFFFF`，表示没有 ADC 实测数据；flags bit0 默认 0（未使用软件电源开关），bit1 表示固件输出许可，bit2 表示锁定。

## 可执行的上板方案

### 阶段 0：核对驱动接线和安全条件

1. 对照你们手头的开发板原理图、底板接线和 BTS7960 实物丝印确认每根线。
2. USART3 接 PB10/PB11，USB-TTL 使用 3.3 V 逻辑并共地。
3. BTS7960 的逻辑 VCC、电机动力、GND、RPWM、LPWM、EN 按模块实际接线图核对。当前固件默认不驱动 EN，EN 需按已确认的模块接法处理。
4. PB4/PB5 与 W25Q128 有复用，PB0/PB1 与触摸屏信号复用；电机 PWM 占用这些脚时对应板载外设不能同时使用。调试选择 SWD；PA15/PB3 不可同时作为完整 JTAG。
5. 准备独立物理断电开关/急停。软件命令无法覆盖 MCU 卡死、引脚短路或驱动器损坏。

### 阶段 1：构建固件并检查串口

GCC 10.3.1 命令行构建已成功，`.elf`、`.hex`、`.bin` 产物位于 `C1_GCC/build/`。Keil 工程构建和真机烧录尚未验证。需要重建时，在 PowerShell 执行下面的命令；脚本会从 PATH 自动查找 `arm-none-eabi-gcc`。不要假定仓库原有的 `release/C1.hex` 已包含这版代码。

```powershell
& .\C1_GCC\build.ps1
python tools\serial_tester.py -p COM3 monitor
```

先看到 IDLE、左右速度 0、里程 0；电压显示未知是预期行为。

### 阶段 2：不接电机动力，确认编码器比例和方向

通过串口先清里程，再观察状态；手动准确转动一侧车轮一整圈。该侧里程应接近 565.5 mm，反向转动应反号。若比例不符，按实测修正 `ENCODER_COUNTS_PER_WHEEL_REV`；若方向反了，将对应 encoder sign 改为 -1。

```powershell
python tools\serial_tester.py -p COM3 reset-odo
python tools\serial_tester.py -p COM3 monitor
```

以上状态只上报毫米，不直接上报原始 TIM 计数，因此每轮计数要通过理论周长/观测里程比例换算，或用 `tools/encoder_calib.py` 按实际行程标定。

### 阶段 3：架空车轮，单次低速双轮检查

确认编码器有效、方向正确后，架空驱动轮，用限流电源先发低速持续命令：

```powershell
python tools\serial_tester.py -p COM3 drive 50 50
```

`drive` 每 100 ms 续发目标，使通信看门狗保持有效；按 Ctrl+C 会发送软停。任何轮向不对、编码器反馈符号不对、异常声响或电流升高，立即用物理开关断开电机动力。

不要在编码器未确认时给长时间速度命令：如果反馈线断开，PI 会把“速度仍为零”理解为误差一直存在，逐渐增加 PWM。当前堵转检测默认关闭，不能依赖它保护测试。

### 阶段 4：逐轮调 PI，再做双轮测试

每次只调整一项，记录目标速度、实际速度、PWM 和电流。参数通过串口写入但掉电不保存：

```powershell
# 先令积分为 0，只看比例响应
python tools\serial_tester.py -p COM3 pid 0.3 0

# 稳定后逐渐增加积分项，例如从较小值开始
python tools\serial_tester.py -p COM3 pid 0.3 1.0
```

每次 `pid` 命令会重新设置两项参数并清空积分；建议先低速、小幅度调整。若出现持续震荡或速度明显超过目标，先发 stop 并检查反馈比例、正负方向和电机接线，不要继续加大增益。

### 阶段 5：增加真实硬件保护后再落地

电池电压、母线电流还没有 ADC 测量实现；请接入并校准相应检测电路。堵转检测应在每轮计数和方向确认后，再评估是否开启 `STALL_DETECT_ENABLE`。软件急停需与独立硬件断电链路配合。完成这些以后再做地面直线、转弯、制动和通信失联测试。

## 现在可以依赖什么，不能依赖什么

| 可以作为当前软件行为理解 | 不能当成已验证功能 |
| --- | --- |
| GCC 10.3.1 命令行构建成功，产物已生成 | Keil 工程也已构建、或已在开发板运行 |
| 协议帧解析、命令队列、速度斜坡、PI 计算和状态机的源码 | 3584 counts/rev 已符合你们编码器实物 |
| 软件 PWM 归零、通信超时软停、软件锁定 | 独立硬件急停、真实电流限制、欠压切断 |
| `0xFFFF` 明确表示电压未知 | `flags` bit0 代表电机电源真实存在 |

先把接线、计数和方向确认，再调 PI；这三件事的顺序不能颠倒。完整字段定义见 [`docs/02_上下位机通信协议.md`](../docs/02_上下位机通信协议.md)，硬件清单见 [`docs/04_硬件联调步骤.md`](../docs/04_硬件联调步骤.md)。
