## 一、硬件分工

### Q1：运动控制是不是由电机驱动板搞定的？我们只是去控制驱动？

**后半句对，前半句不对。**

BTS7960 是**纯功率放大**的 H 桥，它不做任何控制：

| 它做 | 它不做 |
| --- | --- |
| 把 PWM 信号放大成 12V / 大电流 | 不知道电机转多快（没有编码器接口） |
| 按 RPWM/LPWM 的高低决定电流方向 | 没有速度环、不会调速、不会限流 |

正确的分工：

```
STM32（做控制）                    BTS7960（出力气）        电机
速度环 / 加减速斜坡 / 方向逻辑 / 限流 / 急停   →   只是把 PWM 放大   →  转动
```

所以"运动控制"是 C1 的活，算法全在 STM32 里。

### Q2：编码器的数据是不是从驱动板读的？

**不是。BTS7960 根本没有编码器接口**（它只有电源、电机、PWM 这些引脚）。

实际接线：

```
编码器 A/B 两相  →  STM32 引脚（左轮 PA15/PB3，右轮 PC6/PC7）
STM32 用定时器的「编码器模式」硬件四倍频计数，主程序 100Hz 读一次
```

也就是说：**编码器直接接 STM32，不经过驱动板。**

### Q3：电机和轮子怎么连的？

用**联轴器**直连（电机轴 → 联轴器 → 轮轴），1:1 传动，没有额外减速。所以减速比就是电机自身的 1:56。

> 装的时候注意联轴器内径要和电机轴径匹配（JGB37-555 一般是 6mm 带铣扁），不然装不上。

## 二、通信

### Q4：上下位机通信的格式是什么？

一句话：**`AA 55` 帧头 + 长度 + 序号 + 命令 + 数据 + CRC16 校验**。

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| `AA 55` | 2 B | 固定帧头 |
| LEN | 1 B | 后面还有多少字节 |
| SEQ | 1 B | 序号，查丢帧用 |
| CMD | 1 B | 命令码 |
| DATA | N B | 数据，小端序 |
| CRC16 | 2 B | CRC16-Modbus，覆盖 LEN 到 DATA |

**命令码**：`0x01` 设置轮速 / `0x02` 软停 / `0x03` 急停 / `0x04` 清除急停 / `0x05` 里程清零 / `0x10` 状态上报 / `0x7F` 应答

**速率**：115200 8N1；上位机 10Hz 发指令，下位机 20Hz 上报状态。

完整定义见 [`02_上下位机通信协议.md`](02_上下位机通信协议.md)。

### Q5：怎么快速验证协议实现对不对？

用这两串固定字节对一下（带真实 CRC，可直接用）：

```
设置左右轮 200mm/s：AA 55 06 01 01 C8 00 C8 00 28 B1
状态上报：        AA 55 13 02 10 02 00 2E 30 C8 00 C8 00 00 68 0D 00 00 00 00 00 00 F3 EE
```

电脑端工具：`python tools/serial_tester.py selftest`（不接硬件就能跑）。

### Q6：通信断了会怎么样？

分级保护，不会直接趴窝：

| 情况 | 下位机动作 |
| --- | --- |
| 500ms 没收到帧 | 斜坡减速到 0（软停），还能恢复 |
| 1s 还没恢复 | 急停锁定，**切断电机电源**，要重新上电或发清除命令 |
| 还没收到过第一帧 | 不判断超时（树莓派开机慢，不会误判） |

## 三、控制算法

### Q7：控制器用的什么？PID 吗？

**增量式 PI 速度环，200Hz**（每 5ms 算一次），不是完整 PID。

| 环节 | 用不用 | 原因 |
| --- | --- | --- |
| P 比例 | ✅ | 主力，误差越大出力越大 |
| I 积分 | ✅ | 消除稳态误差，让实际速度精确跟到目标 |
| D 微分 | ❌ | 速度信号有噪声，微分会把噪声放大，车会抖 |

除了 PI，还有三层处理：

1. **斜坡限幅**——目标速度按最大加速度（500mm/s²）逐步逼近，实现软启动，防止窜车和电流冲击
2. **死区补偿**——占空比低于 8% 时电机不转，直接输出 0，避免堵转发热
3. **电流限幅**——估算母线电流超过 8A 就降速（电池持续放电只有 10A）

### Q8：位置控制 / 路径跟踪在下位机做吗？

**不做。** 分工是：

```
树莓派（ROS2）：导航算法 → 算出"应该以多少速度走" → 发 /cmd_vel
STM32（下位机）：收到速度指令 → 控制两个轮子精确转到这个速度
```

下位机只负责"**让我以 X mm/s 转**"这一层，不管"往哪走"。

### Q9：STM32 怎么知道轮子实际转多快？

编码器 → 定时器硬件计数 → 每 10ms 读一次增量：

```
转速(mm/s) = 计数增量 × 0.2295(mm/计数) × 100
```

其中 0.2295 = π×180mm ÷ 2464 计数（轮子一圈 = 565.5mm，编码器 2464 计数）。

## 四、传感器与 IMU

### Q10：IMU 数据谁来读？

**下位机只负责读出来 + 透传给树莓派**，不在 STM32 上做姿态融合。

> 前提：IMU 型号和接口还没确定（I2C 还是 SPI）。确定后 `Task_Sensor` 里补上即可。

### Q11：位姿推算（姿态解算）在哪做？

**建议在树莓派做**，用 **EKF 融合**：

```
输入：编码器里程计（下位机上报的左右轮里程）+ IMU（角速度/加速度）
输出：/odom（位置 + 朝向）
工具：ROS2 的 robot_localization 包，现成可用
```

放上位机的理由：融合要算矩阵、要调参，改起来方便；STM32 的算力留着跑控制环更值。

树莓派侧的换算公式（`Δodo_L`、`Δodo_R` 是两个轮子这段时间各走了多少毫米，`L` = 轮距 428mm）：

```
Δs = (Δodo_R + Δodo_L) / 2      前进距离（两轮平均值）
Δθ = (Δodo_R − Δodo_L) / L      转角（右轮多走 = 左转，反之为右转）
```

> 注意别弄反：**和**算前进、**差**算转向。

## 五、工程实现

### Q12：为什么用 HAL 库不用标准库？

1. ST 官方从 2016 年起就停止维护标准库了，新教程新例程基本都是 HAL
2. UART 的 DMA/中断、TIM 的编码器模式、看门狗，HAL 都有现成封装，排查问题方便
3. **性能不是问题**：20kHz PWM 是硬件定时器自己产生的，CPU 只在 200Hz 的速度环里改一下比较寄存器

如果课程要求标准库，协议层和控制逻辑层（`protocol.c` / `app_tasks.c`）**一行都不用改**，只需重写初始化部分。

### Q13：为什么用 FreeRTOS？裸机跑不行吗？

任务书明确要求（"基于 FreeRTOS 划分任务"）。而且实际也有好处：

- 安全监控必须**独立于**控制逻辑——裸机里要是控制循环卡住，安全逻辑就一起卡住了
- 通信解析、控制、安全监控节奏不同（事件驱动 / 200Hz / 1kHz），用 RTOS 各自独立更清晰

| 任务 | 优先级 | 周期 |
| --- | --- | --- |
| 安全监控 | 最高 | 1kHz |
| 速度环 | 高 | 200Hz |
| 编码器 | 中 | 100Hz |
| 通信 | 中 | 事件驱动 + 20Hz 上报 |
| 看门狗维护 | 最低 | 1Hz |

### Q14：为什么上电以后电机不动？是不是坏了？

**不是，这是设计如此。** 上电默认：

- 驱动电源开关是**断开**的
- PWM 输出全 0
- 状态是 IDLE

只有收到上位机的**速度指令**，才会先合闸、再使能、再转动。这是为了防止上电瞬间车自己窜出去。

调试时如果电机不动，先看状态帧里的 `flags`：**bit0 = 1 表示电源已合闸**，是 0 就说明还没收到过有效指令。

### Q15：急停是怎么实现的？

**断电。** STM32 用 PA0 控制底板那路电源开关，急停时直接切断电机驱动板的 12V。

为什么不用纯软件停：软件停靠的是"程序正常运行"这个前提，万一程序跑飞就失效了；断电是物理层面的，MCU 死机也照样断。
